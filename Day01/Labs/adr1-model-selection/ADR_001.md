# ADR-001: Model Selection & Deployment Architecture for ClaimsCopilot (v1)

* **Status:** Proposed
* **Date:** October 2026
* **Deciders:** Enterprise AI Architecture Team

---

## 1. Context & Problem Statement
Bharat Suraksha Insurance requires an AI solution (**ClaimsCopilot**) to support 3,200 claims adjusters across India. The workload spans:
1. **High-volume long-context summaries:** 40,000 PDFs/month (~1B input tokens/month, asynchronous).
2. **Interactive RAG Q&A:** 2,500 queries/day (~10M input tokens/day, <8s SLA).
3. **Bilingual customer letters:** 15,000 drafts/month (English & Hindi, <1m SLA).

**Key Constraints:**
* Strict data privacy and India data residency considerations (IRDAI compliance for PII/health data).
* Cost efficiency given massive input token volumes for claim summaries.

---

## 2. Decision Drivers
* **Data Residency & Security:** Policyholder PII (health and motor records) must be hosted in India region data centers or processed within strict enterprise cloud boundaries.
* **Cost Efficiency for Heavy Context Window:** ~1B input tokens per month for heavy document summarization.
* **Multilingual Capability:** High fluency in Hindi and Indian English nuance.
* **Latency & SLA:** Sub-8-second retrieval for live adjuster Q&A.

---

## 3. Options Considered

### Option A: Fully Managed Commercial SaaS APIs (e.g., Azure OpenAI / Google Vertex AI - India Regions)
* **Pros:** Minimal operational overhead, high baseline reasoning, native multimodal PDF parsing, easy scaling.
* **Cons:** High variable cost at 1 Billion input tokens/month for batch summaries; vendor lock-in.

### Option B: Self-Hosted Open-Weights Models (e.g., Llama 3 / Qwen 2.5 on AWS/Azure India Dedicated GPUs)
* **Pros:** Full control over PII/data residency, zero data leaves VPC, cost scales with instance uptime rather than per-token for high utilization.
* **Cons:** GPU infrastructure management (vLLM/TGI), warm-up latency, cold start/scaling complexity.

### Option C: Hybrid Architecture (Recommended)
* **Batch Workloads (Summaries):** Provisioned / Open-Source model deployed on dedicated cloud GPUs (India Region) or Batch Tier commercial API for discounted long-context ingestion.
* **Interactive Workloads (Q&A & Letters):** Serverless enterprise API endpoint (e.g., Azure OpenAI India / Bedrock India) for low-latency RAG and Hindi text generation.

---

## 4. Decision Outcome
**Chosen Option:** **Option C (Hybrid Deployment Approach)**

1. **Workload 1 (Claim File Summary):** Utilize **Batch Processing Endpoints** (or dedicated self-hosted Llama-3-70B via vLLM in an India Cloud Region) to drastically cut token costs for the 1B monthly input tokens while meeting the 2-minute SLA.
2. **Workload 2 (Policy RAG Q&A):** Deploy a managed API with vector database retrieval hosted locally in India to guarantee $<8 \text{ sec}$ latency.
3. **Workload 3 (Customer Letters):** Route through a high-performing multilingual model API with proven Hindi fluency.

---

## 5. Consequences

### Positive
* **Cost Optimization:** Decouples heavy batch ingestion from high-cost real-time inference pricing.
* **SLA Compliance:** Dedicated queues ensure batch summarization doesn't throttle interactive Q&A.
* **Data Governance:** Meets IRDAI compliance by pinning processing to local India cloud zones.

### Negative / Risks
* **Architectural Complexity:** Managing two separate pipelines (Batch Queue vs. Real-time API).
* **Hindi Translation Nuance:** Open-weights models may require fine-tuning or evaluation against enterprise commercial models for accuracy in Hindi legal terms.
